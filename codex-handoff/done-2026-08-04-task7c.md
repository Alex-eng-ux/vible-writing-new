## 关键设计决策

1. **补只读端点而非改写契约**：后端只有写路径（canon-runs/canon-decisions），没有读取正式 Canon 与候选列表的 GET API。本次在 `canon.py` 追加 3 个只读端点（`_candidate_projection` 与领域层 `_to_dict` 字段一致），严格保持"不修改领域契约"（候选表结构、状态机、决策绑定校验均未动）。
2. **决策分批提交对应后端一次性语义**：`submit_canon_decisions` 一次提交后运行进入终态 `accepted`（`run.status in (accepted, ...)` 拒绝后续决策）。因此 UI 把逐条选择（confirm/reject/defer）收集到一批，由"提交决策"统一调用一次 API；行内按钮只是切换选择状态（再次点击取消），不立即发请求。
3. **同一批决策复用同一 `Idempotency-Key`**：`decisionKeyRef` 在首次提交时生成 `canon_decide:{run_id}:...`，失败不清空、重试复用；成功后重置。请求体 `idempotency_key` 与请求头一致（后端强制校验，否则 `COMMAND_CONTEXT_MISMATCH`）。Playwright 用路由拦截制造首次 500 验证两次请求同一键。
4. **场景级确认的展示语义**（计划第 174 行："该确认显示作用域，不伪装成全局 Story Bible 更新"）：面板对 `scope == "scene"` 渲染固定提示"场景级确认只更新场景局部 Canon，不会改变全局 Story Bible"；正式 Canon 区只反映全局条目（由章节级 confirm 物化）。测试断言场景级 confirm 后正式条目数不变、章节级 confirm 后事实条目才出现。
5. **固定 fixture 与 Fake model**：候选由 `seed-canon-candidates` 播种（内容满足决策前校验：`paragraph_ref`、`effective_story_time.value`、`narrative_knowledge` 枚举、plot_thread 带 `state/planned_resolution`），来源版本取运行 `canon_source_revision_id`，保证后续 `_validate_candidate_bindings` 与 `confirm_canon_decisions` 的来源/作用域/归属校验全部通过；运行推进 `waiting_feedback` 并写 `run_waiting_feedback` 事件。不接入真实模型 API。
6. **章节级运行的前置状态**：章节 Canon 要求章节 `accepted + in_sync + 入口链非 stale`，confirm 来源校验还要求 `entry_handoff_status == "in_sync"`。`seed-chapter-accepted` 经 `aggregate_chapter_revision` + `commit_chapter_version`（自动置 `in_sync`）并显式置 `entry_handoff_status = "in_sync"`。
7. **运行状态回溯**：候选行带 `generation_run_id`，面板刷新时从候选回溯运行 id 并 `getRun` 展示运行状态（等待决策/已接受），决策按钮只在 `waiting_feedback` 显示。

## 范围边界

- 后端 Worker 为占位实现：候选提取由 `seed-canon-candidates` 确定性播种，未执行真实 CanonAgent，也未接入真实模型（Fake model 语义）。
- 后端改动仅为 3 个只读 GET 端点 + schema 只读追加 + 测试播种工具；未修改任何领域契约（候选状态机、决策绑定校验、物化规则均未动）。
- 场景级确认绝不生成全局条目（后端 `confirm_canon_decisions` 场景分支）；UI 只在章节级 confirm 后刷新正式 Canon。
- 决策分批提交：一个 Canon 运行一次决策批次后进入终态；面板不支持同运行二次决策（与后端契约一致）。
- 候选展示与决策依赖运行 `waiting_feedback`；刷新经候选回溯运行 id，不依赖 SSE（Canon 运行未接入页面级 SSE 流）。
