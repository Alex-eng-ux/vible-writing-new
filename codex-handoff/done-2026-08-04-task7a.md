## 目标

在现有后端契约之上提供作者手工编辑入口：

- 手工编辑只通过 `source=author` + `prosemirror_step` 的 ChangeSet 接口提交，绝不直接更新正文或乐观修改 accepted 版本；
- 每次命令动作使用独立 `Idempotency-Key`，请求经 Next.js 代理（前端不直接访问后端端口）；
- 基线过期（SCENE_STALE/SCENE_STATE_INCOMPATIBLE）时只展示本地 vs 服务器差异，由作者选择覆盖或丢弃；
- Playwright E2E 覆盖：创建资源并编辑保存首稿、编辑已有版本并比较、过期基线冲突展示与覆盖提交、手动回滚、所有 POST 命令请求携带 Idempotency-Key。

## 关键设计决策

1. **全部手工写入走 ChangeSet**：编辑器不直接提交正文。保存动作 = 创建 ChangeSet（`base_scene_revision_id` + `operations`，首稿 `insert`、已接受版本 `replace`/`delete`）+ 提交（`author_decision=accept`）。操作形态与后端最小解释器支持范围一致。
2. **基线取 `acceptedDetail.id` 而非 `selectedScene.accepted_scene_revision_id`**：场景列表只在打开/刷新时更新 accepted 指针，连续两次保存时该字段仍为旧值（null），会把第二次保存误判为基线过期（SCENE_STALE）。当前已加载的 accepted 详情（保存后已刷新）才是权威基线；仅当无任何版本时基线为 null（首稿 insert）。
3. **比较选择随版本刷新同步**：保存/回滚后调用 `refreshSceneLatest` 时同步设置 左=倒数第二个版本、右=最新版本；否则第二次保存后左右仍指向同一旧版本，比较按钮提示"请选择两个不同版本"。
4. **冲突只展示不自动合并**：SCENE_STALE 时加载服务器最新版本，DiffView 展示"服务器最新 vs 我的本地"；作者选择"以我的文本覆盖提交"（基于最新版本重建 ChangeSet）或"丢弃我的更改"（编辑器恢复服务器内容）。本地文本状态（`localText`）由编辑器 onChange 驱动，不与 accepted 版本乐观同步。
5. **幂等键自动生成**：每个动作（创建项目/卷/章/场景、创建 ChangeSet、提交、回滚）使用独立键（`createIdempotencyKey(command, resource)`），E2E 断言所有 POST `/api/*` 请求都携带。
6. **独立 E2E 数据库**：globalSetup 调用 `e2e_bootstrap` 创建/重置 `novel_e2e` 库，webServer 后端使用该库，不污染开发库与 pytest 测试库；测试串行运行避免共享库命名冲突。
7. **前端不直连后端**：所有请求经 Next.js 代理（`next.config.mjs` rewrites）；浏览器只访问 3000 端口。

## 验证结果

- `npx playwright test`（frontend）：**5 passed**，覆盖：
  1. 创建项目/卷/章/场景并通过 UI 编辑保存首稿 → 历史出现 1 条 accepted 版本；

- `npm run typecheck`（frontend）：`tsc --noEmit` **通过**。

## 范围边界

- 只做作者手工编辑路径：未接入 ReviewAgent/一致性自动修订/Story Bible UI（后续 Task）。
- 编辑器操作仅支持后端最小解释器的 insert/replace/delete 文本操作；未实现富文本结构级差异（diff 按行）。
- 冲突覆盖为"以本地文本为基准重建 ChangeSet"的整段替换语义，无逐段三方合并。
- 未改动后端领域契约；`GET /api/scenes/{id}/revisions/{rev_id}` 只读端点已确认存在并被前端消费。
- E2E 库 `novel_e2e` 由 globalSetup 每次重建，测试串行、无并发。
